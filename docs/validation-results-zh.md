# Context 工具验收与验证结果

日期：2026-11-02  
范围：Context core v0.3.1 与 Multiverse 原生 OpenCode 集成。本文只报告当前样例和运行配置下的证据。

## 功能验收

一次真实 A→B→A 交接最终完成：A 发布研究结果，B 在自己的会话中复算和复核，A 读取复核后更新研究状态。该验收经历了分阶段人工恢复和多次继续运行，因此证明原型可以完成该流程，不证明无人值守可靠性。

当时的确定性测试为 42 项 Python 测试和 447 项 Rust 测试通过。协议机制也有单独负例检查。测试通过只支持实现行为，不代表 Context 让 Agent 的研究结果更好。

## 三层受控预实验

正式对照包含 90 个单元，覆盖 6 个合成检查点、每个条件 3 次重复。A 使用 Issue 和原始文件；B 增加普通 Markdown 摘要；C 使用同一摘要内容，通过 Context 按需发现和展开；另有两种机制消融。

| 条件 | 严格完成 | 比例 |
|---|---:|---:|
| A：Issue 与原始文件 | 16/18 | 88.9% |
| B：普通 Markdown 摘要 | 15/18 | 83.3% |
| C：按需 Context | 8/18 | 44.4% |
| C-flat：摘要全文展开 | 10/18 | 55.6% |
| C-no-freshness：不显示新鲜度提示 | 10/18 | 55.6% |

第一层的三条完整无人救场交接链为 0/3 严格通过。各链里有阶段完成了科学计算或复核，但至少一个必需交付或交接门没有通过。另一次分阶段人工恢复的功能验收不与这些严格试次混算。

## 可以得出的结论

在这组短程合成任务和当前运行配置下，没有观察到 Context 的效果优势；严格通过率低于两个对照。C-flat 和 C-no-freshness 也没有显示渐进展开或新鲜度提示带来独立收益。C 组平均耗时更长，但这只是本小样本中的观察，不足以说明所有任务都会更慢。

15 次中断恢复都保留了已验收的旧结果；只有 1/15 次在执行代码中真正跳过了已完成计算。因此不能把“结果没有丢失”表述成“普遍减少了重复计算”。

复核者曾在开始复算前通过 Forgejo Issue 评论看到生产者汇总指标，所以这些复算不能称为盲复核。上下文工具的来源版本检查也不能替代对摘要结论的语义核对。

90 个对照单元中，25 个单元有 27 次模型请求没有可核验的 usage。缺失值按 unknown 处理，不能补成零；没有足够完整配对来比较 token 成本，也没有可靠的费用收益结果。

## 解释边界

这轮验证的任务是受控合成检查点，不是数周的自然科研项目。它足以说明当前实现和评估流程仍有明显失败模式，不足以证明长程研究任务中也没有收益。下一轮计划先把检索、证据判断、说明负担和交付可靠性分开测，再做短链与多阶段接力；计划状态见[CTXVAL-2 方案](ctxval2-plan-zh.md)。

公开仓库刻意不包含原始模型流量、运行转录、凭据和本机环境配置；上述数字来自独立保存的汇总审计记录。
